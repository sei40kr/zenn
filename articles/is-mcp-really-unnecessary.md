最近、AIエージェント界隈で「MCPは要らない」という議論を目にする機会が増えた。
代わりにCLIを直接叩かせれば良い、Agent Skillsで十分だ、といった主張である。

私自身もClaude Codeを日常的に使う立場として、この議論には言いたいことがいくつかある。
本記事では、MCP不要論の論点を整理した上で、CLI直叩きの限界とAgent Skillsの位置付けについて自分の考えを書き残しておく。

# MCP不要論の主な論点

MCP不要論の中心的な主張は、コンテキスト消費の問題である。

MCPサーバーを接続すると、そのサーバーが提供するtoolの説明がセッション開始時にコンテキストへ流し込まれる。
仮に20個のtoolを持つMCPサーバーを接続していても、そのセッションで実際に使うのは1〜2個ということがほとんどだ。
使わないtoolの説明文が常時コンテキストを占有するのは確かに無駄である、というのがこの論の出発点だ。

この指摘自体は正しい。

# Tool Search Toolによる緩和

ただし、Claude Codeに関して言えば、この問題はある程度解消されつつある。

Claude Codeには、サブエージェント側から[Tool Search Tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)経由でMCP toolをkickする仕組みがある。
メインのコンテキストにはMCP toolのスキーマが展開されないため、未使用toolによるコンテキスト汚染は最小限に抑えられる。
この挙動は `ENABLE_TOOL_SEARCH` 環境変数やサーバー単位の設定で切り替えられる。([Configure tool search - Claude Code Docs](https://code.claude.com/docs/en/mcp#configure-tool-search))

他のエージェントでも同様に、MCP toolのコンテキストを含めるかどうかをユーザー側で制御できるようになってきた。
代わりにAgent Skillsの中で必要なMCP toolだけを明示的に呼び出すスタイルが広がっている。

# CLI直叩きには別の弱点がある

ここで「ならCLIを直接叩けばいいじゃないか」という話に戻ると、CLI側にも別の問題がある。

## 学習カットオフ以降のCLIに弱い

新しめのCLIや、最近オプションが追加されたコマンドについて、エージェントは正確な使い方を知らない。
そのままだと存在しないオプションをでっち上げたり、古い構文で叩いて失敗したりする。
`--help` を読ませるなり、ドキュメントを参照させるなりのワンクッションが必要になる。

## コマンドの影響範囲が読みづらい

これがCLIの本質的な弱点だと考えている。
コマンド名から想像できる機能と、実際の影響範囲が乖離しているケースも多い。

例えば `find` は名前の通りファイル検索コマンドだが、`-exec` や `-execdir` を使えば任意のコマンドを実行できる。
つまり「`find` は読み取り専用だから無条件で許可」という雑な設定はできない。
権限制御の観点では、コマンド単位ではなく引数の組み合わせまで見る必要があり、設定が極めて煩雑になる。

`docker run` は一見「コンテナを立ち上げるだけ」のコマンドだが、`--privileged` や `-v /:/host` の付与でホストのファイルシステムを丸ごと乗っ取れる。
サブコマンド単位で許可/拒否を設定していても、オプションや引数次第で安全性は簡単に覆されるのだ。

MCPはこの問題に対する1つの解だ。
そもそもAIエージェントから利用されることを前提に設計されているため、副作用の種類や権限のスコープがtool単位で明確になっている。
CLIのように「コマンド名から実行可能な操作を逆算する」作業が不要で、許可判定に必要な情報が最初から構造化されているのだ。
「これはMCPでなければ実現できない」というよりは、「AI利用を前提にゼロから設計されたインターフェイスの方が権限制御と相性が良い」というのが現実的な評価だ。

# CLIを安全側に倒すための補強策

CLI直叩きの弱点に対しては、現状すぐに使える補強策と、長期的にCLI側の設計を変えていく方向性の2つがある。

## sandbox + ホワイトリスト方式

1つ目は、現状すでに使える補強策だ。
コマンドそのものをsandboxに閉じ込めてしまえば、許可リストの粒度が粗くても横方向の被害範囲を抑え込める。
Claude Codeは標準でsandbox実行をサポートしており、ファイルシステムやネットワークのビューを限定した空間でコマンドを走らせられる。

特定のパスやホストへのアクセスが必要なコマンドについては、sandboxの制限をホワイトリストで個別に緩めれば良い。
「デフォルトは閉じておき、必要な穴だけ明示的に開ける」という運用が現実的だ。

## AI-safeなCLI設計

もう1つは、CLIそのものがAI前提の設計に置き換わっていく長期的な方向性だ。
具体的には以下のような変更が考えられる。

### 引数順序を「動詞 → リソース種別」の順に揃える

現状のCLIは「リソース種別 → 動詞」の順で引数を取る設計が多い。

- `docker container rm <name>`
- `docker image prune`
- `gcloud compute instances delete <instance>`
- `az vm delete <name>`

この順序のままだと、許可判定のためにコマンドを末尾まで読まないと操作の種類がわからない。
これを「動詞 → リソース種別」の順に反転させれば、先頭のprefixだけで危険度を機械的に判定できる。

- `docker rm container <name>` → `docker rm` を見れば削除系と確定
- `gcloud delete compute instances <instance>` → `gcloud delete` で同上
- `az delete vm <name>` → `az delete` で同上

結果として「`docker rm` は承認必須」「`docker ls` は常時許可」のような粗い粒度のルールで十分安全側に倒せる。

### 任意コマンド実行を招くオプションを廃止する

例えば `find -exec` は、本来「ファイル検索」のためのコマンドでありながら、検索結果に対して任意のシェルコマンドを実行できてしまう。
このようにコマンド名から想像できない副作用を持つオプションは、新設計では削除する。

ただし `coreutils` のように互換性を最優先すべき古参のCLIは、この方向に動くのは難しいだろう。
新しく書かれるCLIから少しずつそうなっていく、というのが現実的なシナリオだろう。

# Agent Skillsの位置付け

先に触れたAgent Skillsについて、ここで改めて整理する。

Agent Skillsの実体は、特定のタスクに必要なプロンプト・権限設定・helper scriptを1つのパッケージにまとめ、エージェントが必要に応じて呼び出せるようにする仕組みだ。
MCPやCLI直叩きと比べた利点は、エージェント側で完結できる点と、内部でCLIとMCP toolを自由に組み合わせられる点である。

Skillの存在をエージェントに知らせるためには、Skill名と説明文のインデックスを常時コンテキストに載せておく必要がある。
個々のSkillの中身は遅延ロードできるとはいえ、インデックス分のコンテキスト消費はMCPと同様に発生する。

ただしSkillはユーザーが `/skill-name` の形で明示的に呼び出せる仕組みを持っている。
人間側が「このタスクはこのSkillでやる」と判断して呼び出すなら、Skillのメタデータをコンテキストから省略してしまうという選択肢も取れる。
この点はMCPよりも運用の自由度が高い。

# まとめ

MCP不要論の出発点となるコンテキスト消費問題は、Tool Search Toolの普及によってかなり緩和されている。
一方、CLI直叩きには「コマンドの影響範囲が読みづらい」という別の弱点があり、現状はsandboxによる隔離で覆い、長期的にはAI-safeなCLI設計への移行で補う必要がある。

Agent Skillsはエージェント側で完結できる第三の選択肢で、明示的kickを前提にすればメタデータのコンテキスト消費も回避できる。

結局のところ、CLI・MCP・Agent Skillsはトレードオフの異なる選択肢であり、用途に応じて使い分けるのが当面の現実解だろう。
長期的には、AI-safeなCLI設計が広がり、その知識をインプットした学習モデルが登場することで、バランスは変わっていく可能性がある。
それまではMCPを「AI利用を前提に設計された権限制御レイヤー」として使い続ける場面は残るだろう。
